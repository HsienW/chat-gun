# Proposal：訂單請求必須發起 Tool 呼叫（修復 F-L1）

## Why

### 問題

使用者在 Gun Shop 只說「幫我把訂單 ORD-1001 退款」時，流程不會進入審批。使用者收到「請提供訂單編號，以及要申請退款或取消的內容」，即使訂單編號已經提供。

`chain-eval-v1` 的 live 評測（2026-10-27）記錄為已知限制 F-L1：test split 10 題只過 3 題，操作 terminal 正確率 0.222。7 個失敗案例的 `approvalRequested` 都是 false，人工決定都沒有送出。因此拒絕、逾期、生效前取消、並行去重、回應遺失與預先核准注入，在 live 下都沒有真正走到對應路徑。

### 根因

失敗層級是 Backend 的 `order_request` 節點（模型決定是否發起 Tool 呼叫），不是 BFF、Frontend、Tool 或評測斷言。兩輪唯讀探針（2026-10-31，qwen3.7-plus，溫度 0）確認了兩個原因：

1. Tool Schema 要求 `reasonCode`，但 Prompt 沒有定義未提供原因時的行為。模型會用文字追問，不發起呼叫。
2. 模型會用文字向使用者索取核准，而審批卡片要等 Tool 呼叫後才會產生。

deterministic 評測沒有發現問題，因為它以腳本產生 Tool 呼叫，跳過了模型決策。

| 探針組別 | 未帶原因 | 帶原因 | 對照組 |
|---|---|---|---|
| 現行 Prompt＋必填 | 0/21 | 12/12 | 未測 |
| 現行 Prompt＋選填 | 11/21 | 10/12 | 未測 |
| 新規則＋必填 | 35/35 | 20/20 | 25/25 |
| 新規則＋選填 | 35/35 | 20/20 | 25/25 |

探針只驗證 `order_request` 單一步驟，不代表整條鏈路通過，而且訊息與規則不是獨立樣本。

### Golden v1 結果（2026-10-31）

`order-request-golden-v1` 對 `shopping-order-request-v2`（qwen3.7-plus，溫度 0，每則 5 次）未通過：單筆變更 22/22、多筆 4/4、聲稱預先核准 4/4，對照 9/11，未完成與無效參數皆為 0。

- 「如果我想退 ORD-1001，會發生什麼事？」5 次有 4 次發起退款請求，原因為 `other`。
- "Hypothetically, could ORD-1002 still be refunded?" 5 次有 2 次呼叫 `order_operation_status`。

未發起呼叫的問題在此資料集沒有再出現，但 v2 對只是詢問的訊息誤觸發。審批閘門仍在，不會造成未核准的退款，但使用者會收到沒有要求的審批。v1 prompt 未跑過此資料集，因此「v2 造成誤觸發」是推論，尚無前後對照證據。Master 於 2026-10-31 決定修訂並重驗。

### Golden v2 結果（2026-10-31）

`order-request-golden-v2` 對 `shopping-order-request-v3` 未通過：單筆 29/29、多筆 4/4、聲稱預先核准 4/4、對照 19/20，變更 Tool 誤觸發 0。「我还在考虑，ORD-1004 现在还能取消吗？先别动它。」5 次有 4 次呼叫唯讀的狀態查詢。Master 決定接受此限制並修訂驗收規則；這是看到結果後的放寬，結果 MUST 標示「通過但有已知限制」，MUST NOT 標示為通過。

## What Changes

### 目標

1. 訊息已識別訂單並要求退款或取消時，模型 MUST 發起對應 Tool 呼叫，由既有審批流程接手。
2. 未提供原因時使用既有的 `other`，不追問。
3. 未發起呼叫時，回覆不得暗示使用者沒有提供訂單編號。
4. 評測可直接診斷模型未發起呼叫的情況，並標示審批閘門未被執行。
5. 以未看過的訊息驗收，並重跑 live 評測，再決定是否解除 F-L1。
6. 只是詢問假設、可行性或流程的訊息 MUST NOT 發起變更 tool 呼叫，也 SHOULD NOT 發起狀態查詢；以問句形式請系統代為執行的訊息仍 MUST 發起呼叫。

### 非目標

- 不修改 Tool Schema：探針顯示 Prompt 修正搭配必填已足夠，且改動面最小。
- 不支援多輪補充原因或訂單編號；使用者仍須在同一則訊息提供訂單編號。
- 不修改審批、冪等、ledger、reconciliation 或權限語意。
- 不切換模型；qwen3.5-flash 的驗證屬於 Chapter 1B。
- 不修改 `chain-eval-v1` 的案例或既有結果。
- 不修改 `order-request-golden-v1`、其結果或 Golden 門檻。
- 不新增回答假設性問題的能力：這類訊息仍得到既有固定回覆，不會得到實質答案。

## Capabilities

### Modified Capabilities

- `approved-order-operations`：新增訂單請求的 Tool 呼叫發起行為。
- `commerce-assistant`：不可信內容涵蓋使用者訊息聲稱已預先核准的情境。
- `retrieval-evaluation`：新增未發起呼叫的可診斷性、provenance 與獨立 Golden 驗收。

## Impact

- **受影響套件**：僅 `backend`。Frontend 與 BFF 沒有契約變更。
- **能力域**：訂單操作、商務鏈路評測。
- **事件與錯誤碼**：不新增。評測 observation 與 provenance 只增加向後相容欄位。
- **外部文件**：live 重跑後才可更新評測文件的數字。

## Risks

- **審批卡片變多**：模型可能對只是詢問的訊息發起呼叫。呼叫只會建立待審批申請，不會執行；Golden 納入假設性問句，超過門檻則不通過。
- **`other` 語意變寬**：`other` 同時代表「使用者說其他」與「未提供」，下游無法區分。Master 已於 2026-10-31 接受此限制，範圍僅限合成資料階段；接正式 Provider 前必須重新評估。
- **反向退化**：收緊假設性問句可能讓真正的請求不再發起呼叫，也就是 F-L1 復發。Golden v2 保留 v1 全部案例，並新增問句形式的請求。
- **模型相依**：結果只適用於驗收使用的模型；換模型時必須重跑 Golden。
- **Prompt 過擬合**：以未看過的訊息驗收。未通過時依反覆失敗停止線處理，不繼續疊加 Prompt 範例。

## Rollback

還原 Prompt 與 Prompt 版本、回覆文案。評測新增欄位為向後相容，可保留。沒有資料遷移；已建立的操作與 ledger 紀錄不受影響。
